## 2. 【关键发现】没有两个章节是同构的

按「去空白 + 数字归一化为 N」后取 md5 去重：

```
104 个函数  →  104 个唯一结构  →  重复组 0 个
```

⇒ **不存在"复制粘贴的章节"**。数据化能省掉的是**样板**，不是**重复内容**——这一点必须先承认，否则会高估收益。

## 3. 但控制流高度规整（数据化的真实空间）

对全部 36 个文件做穷举分类：

### 149 个 `if` 条件的分布

| 类别 | 数量 | 能否表化 |
|---|---|---|
| 定时器/计数器阈值比较（`if (game.rainT > 0.2)` 这类） | **77** | ✅ 可——本质是 `timer()` 包的"到点开火" |
| 其它（含杂项组合条件） | 32 | ❌ 需富 schema 或留代码 |
| 游戏状态查询（`game.*` 组合） | 16 | 🔶 部分 |
| 波次取模/相位（`wave % N === N`） | **12** | ✅ 可——"第 N 波特殊"是表项 |
| 样式枚举分支（`style === 'wall'` 等） | **12** | ✅ 可——`style` 本身已是数据 |

### 53 个 `for..of` 循环的分布

| 类别 | 数量 |
|---|---|
| **固定字面量数组**（绝大多数是 `for (const side of [-1, 1])` 左右对称） | **50** |
| 实体容器遍历 | 0 |
| 其它 | 3 |

⇒ **~50/53 的循环是"左右对称 spawn"**，可以塌缩成数据里一个 `sides: 2` 或 `mirror: true`。

### `timer()` 调用的规整度

| 指标 | 数值 |
|---|---|
| `timer(...)` 调用总数 | **196**（分布在 **85/104** 个函数里；19 个函数完全不用 timer） |
| 每函数 timer 数 | 中位 **2**，最大 5 |
| 不同 key 数 | **27**；最常用 `ring`(50) / `aim`(29) / `s`(26) / `laser`(21) / `spin`(18) / `rain`(17) |
| 间隔值 | min 0.06、中位 0.60、max 2.20；**唯一值 39 个** |

⇒ **`timer` 的"形状"极其规整（key + interval + callback），但数值高度个性化（39 个不同间隔）。**
这正是"表 + 少量表达式"最擅长的形态：**结构进表，数值留数据**。

## 4. 现有抽象已经做到哪一步

`js/stages/_shared.js`（183 行）已提供：

- `mob` / `elite` / `boss` 三个敌机工厂（`_shared.js:7-38`）
- `timer(e, key, interval, dt, fn)` 计时器壳（`:40-46`）
- `scaleN` 难度发数缩放（`:49-51`）
- `faceDefaults` / `midChapter` / `letterChapter` 章节元数据工厂（`:60-135`）
- **`installMidWave`**（`:147-162`）：`continuous` 先 tick、再 `onWave` 门控；支持仅 continuous（不推进 `waveCount`，避免误判 `wavesExhausted` → "打死精英提前清章"）
- `pushBossRef`（`:171-183`）

一个典型章节长这样（`js/stages/a4/mid.js:15-30`）：

```js
export function chapter_a4_mid_1(g) {
  installMidWave(g, {
    interval: 0.7, maxWaves: 13,
    onWave: (game) => {
      const e = mob(40 + Math.random() * (LOGICAL_W - 80), -20, 35, '#fbbf24');
      e.vy = 1.1;
      e.script = (en, d, gm) => {
        timer(en, 's', 0.75, d, () => {
          spawnAimed(gm, en, gm.player, { n: 2, parity: 'odd', type: 'dot', speed: 2.3, color: '#fbbf24' });
        });
      };
      game.spawnEnemy(e);
    },
  });
}
```

⇒ **外壳已经抽象好了**；每章剩下的实际内容是「刷什么怪 + 每只怪的开火表」。

## 5. 由此得到的判据

| 问题 | 数字给出的答案 |
|---|---|
| 有"复制粘贴的章节"吗？ | **没有**（104/104 唯一）。所以"消重"不是理由 |
| 控制流规整吗？ | **相当规整**：77/149 是定时器阈值、50/53 循环是左右对称、196 个 timer 形状统一 |
| 数据化的收益在哪？ | **每只怪的开火表**：把 `timer(...) + spawn*(...)` 族塌缩成表项，吃掉那 77+12+12 个分支与 50 个对称循环 |
| 数据化的成本/风险在哪？ | 剩下 **32 个"其它"条件 + 16 个游戏状态查询**需要富 schema（变量/表达式），否则必须留代码 —— 这正是 ECL 用变量与条件换来的能力，也正是它的复杂度来源 |
| 会不会改变手感？ | 必须零观感变化 ⇒ 需要"表驱动的产物与手写等价"的逐帧比对手段 |

### 7.1 规模（21 个文本文件，24,643 行）

| 指标 | 数值 |
|---|---|
| 子程序总数 | **730**（与 `~/Touhou20/README.md` 记录的「730 个子程序」一致 ✅） |
| `ins_*` 调用总数 | **10,160** |
| 行数 | 24,643 |
| **单面道中均值** | **630 条指令 / 60 个子程序 / 1,613 行** |

（README 记录的另一数字「23,760 条指令」应含循环内重复执行或二进制侧计数；我只统计**文本中出现的 `ins_*` 调用**，得 10,160，两者口径不同，不要混用。）

### 7.2 【关键】TH20 也是「共用库 + 每面内容」两层——和我们的结构同构

- `default.ecl`（1,179 行 / 55 子程序）：`BossDead2`、`BossEscapeNoDead`、`BossEscapeSpell`、**`BossInterval`**、`BossItem`、`BossItemPhase`/`2`/`3`、`DeadAttack1/2`、`Ecl_EtBreak`、`MainBossSpell`/`2`、`MainMBossSpell`、`StoneAttackLevel_B1` …… → **这就是我们的 `_shared.js` 对位物**。
- `common.ecl`（85 行）：`WorldWave01`…`WorldWave11` 等**世界/波次驱动**子程序。
- `st01.ecl` … `st07.ecl` + `st0*bs.ecl`（Boss）+ `st0*mbs.ecl`（道中 Boss）：每面内容。

⇒ 架构上我们与 TH20 **已经同构**：共用逻辑一层、每面内容一层。差异只在**语言**（ECL 脚本 vs JS）。

### 7.3 ECL 的语言特征（从 `st01.ecl.txt:1-70` 实读）

```
void GirlA01(var A) {
    ins_500(24.0f, 24.0f);          // 设尺寸
    ins_501(16.0f, 16.0f);          // 设判定
!HL67
    @GirlA01_at() async;            // 异步生成子脚本
!*
    ins_404(1.9634954f + ([-9987.0f] * 0.34906584f), 3.0f);   // 角度 + 变量参与算术
    ins_23(120);                    // 等待 120 帧
    goto GirlA01_448 @ 0;           // 显式跳转
GirlA01_428:
    ins_23(1000);
GirlA01_448:
    if (1) goto GirlA01_428 @ 0;    // 循环
    return;
}
void GirlA01_at() {
    $A = 100;                       // 变量赋值
GirlA01_at_380:
    ins_601(0);
    ins_23([-1]);                   // [-1] 是"占位/待填"常量（工具侧未解析）
    if ($A--) goto GirlA01_at_380 @ 0;   // 计数循环
}
```

**能力要点**：`var` 参数、`$` 变量、**算术表达式**、`if` 条件跳转、`goto` 标签、`async` 子脚本生成、`ins_23(n)` **按帧等待**，以及 `!HL67` / `!E67` 这类**元数据注解块**（设判定位图/精灵/序号等）。
⇒ ECL 的表达力**低于** JS（没有闭包、没有对象、没有数组字面量），但**高于**纯 JSON 表（有变量与条件）。

### 7.4 由此得到的对照结论

| 维度 | TH20 | 我们 |
|---|---|---|
| 单面内容量 | ~60 子程序 / 630 指令 / 1,613 行 | ~15 章节函数 × 887 字符 ≈ 13k 字符（约 10 个章节/面） |
| 内容形态 | 类 C 脚本（编译成字节码） | JS 函数 |
| 共用库 | `default.ecl` / `common.ecl` | `_shared.js`（183 行） |
| 每怪开火表 | `ins_23` 等待串接 + 计数循环 | `timer(en,key,interval,d,fn)` |
| 每指令元数据 | `!HL67` 等注解块（判定位图/精灵/序号逐指令声明） | `spawnAimed` 的 opts 对象 + `hitR/visualSize(type)` 表 |

⇒ **两者是同一模型的两种写法**。ECL 的"等待串接"≈ 我们的 `timer`；ECL 的子程序库 ≈ 我们的 `_shared.js`。
所以「引入 ECL 式 VM 能否省下大量代码」的答案**大概率是否定的**——它换来的是**另一种**写法，而不是**更少**的写法。
真正的收益点应该落在**每怪开火表的样板**（196 个 `timer` 调用 / 77 个阈值分支 / 50 个左右对称循环），而不是重写整层。

## 8. 每面难度/体量对比模型（数学框架）

### 8.1 为什么不能直接比 `speed`

两边版面高度不同：**我方 600**（`js/config.js:4`），**TH20 448**。
同一句 `speed=2.5` 在两边意味着不同的"越屏时间"。所以必须先无量纲化。

### 8.2 基准约定（已核）

| 量 | 我方 | TH20 | 依据 |
|---|---|---|---|
| 逻辑版面 | 450×600 | 384×448 | `js/config.js:3-4`；`runtime_state/state.cpp` |
| 帧率 | 60Hz | 60Hz | 双方 `dt*60` 约定；`Timer` 按帧 |
| 弹速单位 | **px/帧** | **px/帧** | 我方 `js/entities.js:109-111`（`*= dt*60`）；TH20 `polar(velocity, angle, speed)`（`bullet_system/shoot.cpp:20`） |
| 自机判定半径 | **0**（点判定，`config.js:80`） | `collision_percent × base_radius / 100`，默认值**不可得**（`player_entity/collision.cpp:14` 的 `base_radius` 赋值点未追到） | — |
| 自机速度 | 6.8 / 2.15 px/帧 | 数据驱动（`plNN.sht +0x10`），**数值不可得** | `js/config.js:78-79`；`player_entity/initialize.cpp:48` |
| 弹型判定半径 | `hitR(type)`：dot 3 / rice 2 / talisman 4 / medium 6 / large 12 / laser 5 | `styles[type].radius`（50 种，**已解出**：2.0–28.0，中位 4.0） | `js/entities.js` `hitR`；`bullet_system/style_data.cpp`（`bit_cast<float>` 解出） |

### 8.3 归一化量（本文用的三个核心指标）

对每一发弹，取"每秒跨越几个版面高度"与"越屏秒数"：

```
屏高/秒   v_screen = speed × 60 / H
越屏秒数  T_cross  = H / (speed × 60)
```

对每一面，取弹性量：

```
弹密度    λ = 总弹数 / 该面总时长          [发/秒]
体量      V = 总弹数 / 10s                 [发/10秒]（抵掉各面时长差异）
出怪密度  μ = 出怪数 / 该面总时长           [只/秒]
```

### 8.4 反应时间窗口（难度的第一性量）

对某一发弹，从"进入自机可反应区域"到"命中自机"的时间：

```
T_reaction = d_approach / (speed × 60)      d_approach = 自机中心到敌机的纵向距离
```

`d_approach` 两边都取 `H × 0.75` 作为**估计量**（我方 450px；TH20 336px），并明确标注为估计——因为真实值取决于该面敌机停留位置。

`T_reaction` 越小越难。它同时吃掉了"弹速"与"版面尺寸"两个差异。

### 8.5 判定容差（难度的第二性量）

一发弹"擦身而过"时，自机可偏离的最大距离：

```
容差 gap = r_player + r_bullet
归一化   gap_norm = gap / H
```

**注意两边的结构性差异**：
- 我方 `r_player = 0` ⇒ `gap = r_bullet`（**判定完全由弹半径决定**）；
- TH20 `gap = r_player + r_bullet`，且 `r_player` 可被 `collision_percent`（0..100）与 `expanded_collision`（×3.6）调制 ⇒ **有外部调参通道，我们没有**。

所以 `gap_norm` 的对比必须声明："我方是纯弹半径，TH20 含自机半径"。

### 8.6 轨迹复杂度（第三性量，可选）

| 类别 | 我方 | TH20 |
|---|---|---|
| 直线 | `speed` + `angle` | `ins_605(speed, speed_step)` |
| 加速度 | `accel`（沿速度方向） | `ins_605` 的 `speed_step` |
| 角速度（旋转/螺旋） | `spin` | `ins_604` 的 `angle_step` |
| 追踪 | `homing` | ECL 移动指令 / 转向 opcode |
| 重力 | `gravity` | — |
| 分段曲线 | 无 | `ins_400-448`（34 种移动模式 / Hermite） |

可计算的代理量：
```
角度扫描率 ω = angle_step × 60          [rad/s]（TH20 的 ins_604 第二参）
速度变化率 a = speed_step × 60          [px/帧²]（TH20 的 ins_605 第二参）
我方对应：spin（rad/s）、accel（px/帧²）
```
**注意**：我方 capture 已记录 `homing`/`accel`/`spin`，但 TH20 的"追踪/转向"是 **opcode 序列**而非单一字段 ⇒ 这一维度**只能定性对比，不能给统一数值**。这一点必须写清，不能假装算得出来。

### 8.7 明确不可得 / 不可比的（先说清，避免结论被误读）

1. **TH20 自机判定半径不可得**（`base_radius` 赋值点未追到）⇒ `gap` 只能给"仅弹半径"的下界。
2. **TH20 自机速度数值不可得**（无 `.sht` 文件）⇒ 无法比"自机机动能力/单位时间可走多少个 gap"。**这是本模型最大的缺口**，会让"可躲避性"只能从弹侧看，不能从自机侧看。
3. **两边敌机停留位置不同** ⇒ `d_approach` 是估计量。
4. **我方捕获是"不移动的自机"**（脚本里 oddAim/evenAim 的角度因此固定），影响**角度分布**但不影响**发数与弹速**。
5. **`count × rows` 与实际发数**：TH20 一次 `ins_601` 发 `count × rows` 发；我方一次 `spawnAimed(n)` 发 n 发。两者口径都是"调用一次 → n 发"，可比。
6. rank 难度变体（TH20 11.2% 的指令）会让同一发射在不同难度有不同参数 ⇒ 表 B 必须标注"取哪一档"。
