# 内容量现状与扩充展望（约束：流程时长变化 ≤ +30%）

> 日期: 2026-10-05
> 数据来源: 本作侧为**无头实测**（`.scratch/face-capture.mjs`，202 章 × 7200 帧，逐发记录）；
> TH20 侧为**静态解析**（`.scratch/th20-extract-v2.py` / `v3.py`，自带自检）。方法与口径见 [stage-difficulty-model.md](stage-difficulty-model.md)。
> 版本口径: `js/stages/` 当前状态。**未改动任何运行时代码。**

## 0. 结论摘要

1. **现有内容量（可比口径）**：本作 **202 章 / 14 种具名敌机 / 114 次出怪 / 381 次发射调用**；
   TH20 对照 **730 子程序 / 67 个敌机名 / 514 条出怪指令 / 278 次 `ins_601`**。
   即：**敌机种类 TH20 是我们的 4.8 倍；弹幕花样我们略多（1.4 倍）**。
2. **我们内容量的形态是"少敌机 × 多编排"**：14 种敌机上叠了 381 次发射调用，
   而 TH20 把设计预算摊在 67 种敌机上。
3. **期限约束下，"扩充内容"只有两种合法形态**：
   - **并行加密**（同一时限内加层）：不延长流程，但提高瞬时压力；
   - **换装**（新增敌机/弹幕替换现有章）：需要新的美术与行为，成本高但不改流程。
   **顺序加章会直接顶穿 +30%**，除非同步削减别处 —— 见 §2。
4. **建议的分期目标**：先做 **+30–40% 弹幕花样**（并行加密，零流程增量、零美术新增），
   再做 **敌机种类 14 → 20+**（换装式，需要美术）。

## 2. 约束：流程时长变化 ≤ +30%

### 2.1 时长模型（本作现状）

本作的章节时长由**玩法**决定，不是脚本时长：

| 章节类型 | 结束条件 | 实测中位时限 |
|---|---|---|
| 道中 `mid` | `duration` 到时 | **26s**（69 处 `duration`，范围 22–36s） |
| `midboss` | 击破，或时限 | 击破为主 |
| Letter / Boss | 击破，或 `letterTime` 到时 | **46s**（59 处 `letterTime`） |
| EX pattern | 击破推进 | 未逐章测时 |

**主线单面时长下界**（各章时限之和）：
```
≈ 5.2 × 26s（道中） + 6 × 46s（Letter） ≈ 411s ≈ 6.9 分钟
```
> 这是**下界**——实际游玩时长还要加上击破耗时。9 个主线面 ⇒ 约 **62 分钟**（不含 EX）。

### 2.2 +30% 的量化含义

| 口径 | 现值 | +30% 上限 | 允许增量 |
|---|---|---|---|
| 主线单面时长 | ≈ 411s | ≈ 534s | **+123s** |
| 9 面总时长 | ≈ 62 min | ≈ 80 min | **+18 min** |
| 单章道中时限 | 26s | — | 若加章须同步减别处 |

⇒ **"+30% 以内"在时长上是 +123s/面**。这给出两条硬结论：

**结论 A：顺序加章会立刻顶穿。**
一个道中章就 26s，一个 Letter 章 46s。加 3 个道中章 = +78s（占掉 63% 的预算），
加 2 个 Letter 章 = +92s（75%）。**所以"扩充内容"不能靠加章。**

**结论 B：并行加密与换装是唯一零流程成本的扩充方式。**
- **并行加密**：在现有时限内增加弹幕层/相位 → 时长不变（+0%）；
- **换装**：用新敌机/新弹幕**替换**现有章内容 → 时长不变（+0%）；
- 两者都可以用 §4 的验证方式证明"时长仍在 +30% 内"。

### 2.3 并行加密的压力上限

虽然有 +123s/面的时长预算，但**密集度本身有体验上限**——玩家能同时处理的弹幕量是有限的。
以现有数据为锚：

| 参照 | 弹/秒（峰值） |
|---|---|
| 主线面（1–3 面） | 180–215 |
| 主线面（A4–B6） | 632–1194 |
| EX | 2084 |

⇒ **建议把"并行加密"的目标定在不超过上一档的 1.3 倍**：
前 3 面 ≤ 280、A4–B6 ≤ 1550、EX ≤ 2700（峰值口径）。
**这是设计护栏，不是硬指标**——真机手感优先。

## 3. 扩充方向与各自的成本/风险

| 方向 | 提升的单位 | 流程时长 | 美术成本 | 风险 |
|---|---|---|---|---|
| **E1 弹幕花样**（新发射组合，复用现有敌机） | C2 | **+0%** | 无 | 低 |
| **E2 敌机换装**（新建模/配色/标签，替换现有章） | C1 | +0% | **中高**（每敌机需立绘或几何设计） | 中 |
| **E3 相位/分段**（一章内加"变招"，同章时限内） | C2 | **+0%** | 无 | 低 |
| **E4 平行层**（Boss 战中同时存在的轨道数 2→3） | C2 | +0% | 无 | 中（可读性） |
| **E5 加章** | C3 | **+26s/道中、+46s/Letter** | 低 | **顶穿 +30%** |
| **E6 扩 EX**（EX 已 74 章，再加 pattern） | C3/C2 | +0%（EX 不占主线） | 低 | 低 |

**推荐次序：E1 → E3 → E4 → E2 →（E6 随时）**。
理由：E1/E3/E4 **零流程增量、零美术新增**，且直接命中我们"少敌机 × 多编排"的现状；
E2 才是真正补"敌机种类 14 → 20+"的那一项，但它要美术，建议放在后面。

### 3.1 E1 弹幕花样（首选）

**现状**：381 次发射调用，分布在 14 种敌机上。
**做法**：为现有敌机增加发射组合（新 `spawnAimed` 参数组合、`spawnCrossFall`/`spawnGravityRain`/`spawnHLaser` 的新用法）。
**为什么划算**：`js/patterns.js` 已有 10 个工具函数 + `parity`/`spread`/`accel`/`gravity`/`onSplit` 等参数轴，
**新增花样不需要新代码路径**（只需新参数组合），且天然不延长流程。
**上限**：受 §2.3 的密集度护栏约束。

### 3.2 E2 敌机换装（补 C1 的关键）

**现状**：14 种具名 kind；TH20 是 67。
**做法**：新增或替换具名敌机（独立 kind / 配色 / 标签 / 行为），**替换**现有章的 `mob`/`elite` 而非追加。
**成本**：每种敌机需要一套表现（几何或立绘 + 配色）与一套行为（`e.script`）。
按现有 `_shared.js` 的 `mob/elite/boss` 工厂，行为侧成本低；**瓶颈是表现侧**。
**风险**：`AGENTS.md` 有"未知 kind 禁止默认爱丽丝脸"的红线（实现于 `js/sprites.js:33` 的 `PLACEHOLDER_BOSS_SPRITES`），
新 kind 必须显式登记，不能靠回落。

### 3.3 E3/E4 相位与平行层

**E3**：现有章节内加"变招"（例如 Boss 在 50% HP 切换发射组合）。
本作的敌人脚本已是逐帧函数，**加相位不需要新架构**，但要保证"击破时机不变"以维持时长。
**E4**：TH20 的异步子程序可让一个 Boss 同时跑多条轨；本作 `Enemy.script` 是每实体一条轨，
但 `game.waveFn` 的 `continuous` 可挂第二条章级轨（`js/stages/_shared.js:147-162` 已支持）。
⇒ **Boss 战的"多轨"在架构上已有位置**，属于可直接用的能力。

## 4. 验证方式（"+30% 内"必须可证）

**不能只靠感觉。** 三项都要能自动跑：

1. **时长上界（结构性）**：新增/改动不得增加章数以外的时限总量。
   `test/cases-stages.js:114` 已有「有 letter 的章必须 `letterTime > 0`」断言；
   建议扩展为**逐面时限求和断言**：`Σ duration + Σ letterTime` 相对基线增幅 ≤ 30%。
   （这是"下界"口径，见 §2.1 说明。）
2. **压力上界（实测）**：用 `.scratch/face-capture.mjs` 对改动面重跑，
   断言**面内弹/秒峰值**不超过 §2.3 的护栏。
3. **零观感变化（回归）**：未被有意改动的章节必须逐帧哈希一致——
   方法与 [stage-content-plan.md](stage-content-plan.md) §5 的黄金哈希相同（`test/mockGame.js` + 固定 seed + 逐帧状态哈希）。

**建议的验收顺序**：先跑 (1) 证明没顶穿，再跑 (2) 看压力，最后跑 (3) 确认没误伤。

## 5. 尚不确定 / 需要先测的

1. **EX 的逐章时长未测**：EX 74 章是 pattern 型（击破推进），实际占用时长未记录 ⇒
   "+30%" 在 EX 上暂时无法验证。**动 EX 之前应先补这项测量**。
2. **实际游玩时长未采**：§2.1 是**时限之和的下界**，没有真人/录像的真实单面时长。
   ⇒ 建议从录像（`js/replay.js` 已含输入快照）里采一批真实面时长，作为 +30% 的**主口径**。
3. **密集度体验上限未知**：§2.3 的 1.3 倍是**设计猜测**，不是实测结论。需要真机试玩确定。
4. **C2 的口径偏宽**：`acquireBullet` 直接构造的子弹（125 次）与 `spawnAimed` 的批量发射（168 次）
   在"一次调用 = 一次发射"这一层不可加总——前者是逐发构造。作为内容单位时要注意这个差异。

## 6. 建议的分期目标

| 期 | 目标 | 单位增量 | 流程增量 | 前置 |
|---|---|---|---|---|
| **P1** | 现有 14 种敌机各增 1–2 套发射组合 | C2 **+30~40%** | **+0%** | 先定 §2.3 护栏 |
| **P2** | Boss 战引入第 2/3 条章级轨（`continuous` 双轨） | C2 +10% | +0% | P1 的节奏已验证 |
| **P3** | 敌机 14 → **20+**（换装式新增 kind + 表现） | C1 **+40~50%** | +0% | 美术方案 + `sprites.js` 登记 |
| **P4** | EX 再扩 pattern | C3/C2 视需要 | +0%（EX 独立） | **先补 §5.1 的 EX 时长测量** |

**每期都必须过 §4 的三项验证**；任一期的"时长上界"断言红了，就说明该期实质上是在加章，须重新设计。
