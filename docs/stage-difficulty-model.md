# 每面难度与体量对比模型（TH20 ↔ 本作）

> 日期: 2026-10-05
> 参考: `~/Touhou20`（**只读**）的 `scripts/recovered/ecl/`（真实关卡内容）、`bullet_system/style_data.cpp`（弹种半径）、`ecl_vm/`、`player_entity/collision.cpp`。
> 本作侧: `js/stages/`（关卡）、`js/entities.js`（弹体运动与半径）、`js/config.js`（基准量）。
> 工具（均在 `.scratch/`，属分析产物）: `face-capture.mjs`（无头章节捕获）、`face-difficulty.mjs`（率量与反应窗）、`v3.py`（**唯一**的 TH20 ECL 开火提取器，自带自检）、`th20-bullet-radii.json`（50 弹种半径）、`th20-ecl-shots.json`（278 次开火）。
> 获取与使用方式见 [.scratch/README.md](../.scratch/README.md)。
> **未改动任何运行时代码。**

## 0. 结论摘要（含一条反直觉）

1. **容差：两边实质相同。** 两边都是**点判定**（TH20 因 bug 使 `collision_percent = 0`；本作显式 `playerRadius: 0`），
   容差只由弹半径决定：**弹半径 / 版面高 = TH20 0.0054 vs 本作 0.0050**（中位，差 8%）。
2. **但弹速差一倍以上**：中位 **TH20 1.0 px/帧 vs 本作 2.1 px/帧**；按"每秒跨越几个版面高"归一化后 **0.134 vs 0.210（本作快 57%）**。
3. **所以逐发的反应窗口本作明显更短**：越屏秒数中位 **TH20 7.47s vs 本作 4.76s**。
4. **而本作的弹幕**吞吐率是 TH20 的量级级差异**：本作 180–2084 发/秒（按面），TH20 单次开火后等待中位 60 帧（1 秒）。
   ⇒ **本作的难度主要来自"量与速"，不是来自"判定苛刻"。**
5. **一个不能忽略的口径问题**：本作数字是**自由运行沙盒**（自机不动、敌机不死），代表"峰值负载"；TH20 数字是**脚本静态值**，代表"设计意图"。两者不是同一口径，见 §5。

## 1. 为什么必须归一化（模型前提）

| | 本作 | TH20 | 依据 |
|---|---|---|---|
| 逻辑版面 | **450×600** | **384×448** | `js/config.js:3-4`；`runtime_state/state.cpp` |
| 帧率 | 60Hz | 60Hz | 双方 `dt*60` 约定；TH20 `Timer` 按帧 |
| 弹速单位 | **px/帧** | **px/帧** | 本作 `js/entities.js:109-111`（`*= dt*60`）；TH20 `polar(velocity, angle, speed)`（`bullet_system/shoot.cpp:20`） |
| 自机判定半径（**有效值**） | **0（点判定）** | **0（同样是点判定）**：`base_radius = 3.0f` 已确证，但 `collision_percent = 0` ⇒ `0 × 3.0 / 100 = 0` | `js/config.js:80`；`stage_reset.cpp:21`、`collision.cpp:14,48` |
| 自机速度 | 6.8 / 2.15 px/帧 | 数据驱动（`plNN.sht +0x10`），**数值不可得** | `js/config.js:78-79`；`player_entity/initialize.cpp:48` |

⇒ 同一句 `speed=2.5` 在两边不是同一物理量。本模型统一折算为：

```
屏高/秒   v_screen = speed × 60 / H
越屏秒数  T_cross  = H / (speed × 60)
容差占比  gap_norm = (r_player + r_bullet) / H
```

## 2. 数据获取方式（可复现）

### 2.1 本作：无头实测，不是读代码估算

`.scratch/face-capture.mjs` 用 `test/mockGame.js` 的轻量替身（不启 Canvas/Audio/DOM）逐章 `build()`，
注入固定 seed 的 `createRng`，按 `dt = 1/60` 驱动 `waveFn` 与每只敌机的 `script`，**记录每一发**：

```
{ t, speed(= hypot(vx,vy)), r, type, life, homing, accel, laserLen }
```

- 覆盖 **202 个章节**；默认样本 **7200 帧 = 120s/章**（输出 ~100MB JSON）。
- **踩过的坑（重要）**：`Bullet.speed` 字段只在走 `speed` 路径时存在，约一半子弹只给 `vx/vy`
  ⇒ 必须用 `hypot(vx,vy)` 作弹速，否则会多出 10,817 个 `speed=0` 的假样本。

### 2.2 TH20：静态解析真实 ECL 脚本

`.scratch/v3.py` 逐行解析 `scripts/recovered/ecl/*.ecl.txt`（21 个文件），提取：
`ins_601`（开火）+ 该队列最近一次 `ins_602/604/605/606/607` 的参数 + 其后最近的 `ins_23(n)`（等待帧数）。

- **自带一致性自检**：解析出的 `ins_601` 次数必须等于原文中 `ins_601(` 的出现次数。
  **278 / 278 通过**。
- **踩过的坑（都记下来，避免你复核时重走）**：
  1. ECL 的 `[-9987.0f]` / `[-1]` 是**槽位记法**，方括号不是分组；早期把 `[` 当括号深度、`]` 不算，导致参数全错。
  2. ECL 标签形如 `Boss1_at_1040:`，早期用 `^(\w+)\s*\(` 判子程序头会误判标签，**每遇标签就重置状态**，把事件全丢掉。
  3. `op` 是 `int`，早期比较写成 `op == '601'`（字符串），**一个分支都进不去**。
  4. 子程序头处**不能重置 `pending`**，否则每个子程序的**第一条** `ins_601` 被丢掉（762 个子程序头 vs 278 条开火 ⇒ 只剩 52 条）。
- `ins_601` 出现 **278** 次（我曾一度按 `grep` 数成 52，是文本与口径混淆）。

### 2.3 弹种半径（TH20）

`bullet_system/style_data.cpp` 每个 `Style` 块尾部是
`,std::bit_cast<float>(0x4019999au),0x5u,...`，即 **radius = 该 32 位浮点位型**（`0x4019999a` = **2.4f**）。
解出全部 **50 个弹种**：半径 2.0–28.0，中位 4.0，**13 个唯一值**。

## 3. 对比结果

### 3.1 弹速（**可比**）

| 来源 | 中位 px/帧 | P95 | 最大 | 屏高/秒 中位 | 屏高/秒 P95 | 越屏秒 中位 | 越屏秒 P95 |
|---|---|---|---|---|---|---|---|
| TH20 | **1.00** | 3.00 | 5.00 | **0.134** | 0.402 | **7.47** | 2.49 |
| 本作 | **2.10** | 3.20 | 11.20 | **0.210** | 0.320 | **4.76** | 3.12 |

- 原始值本作是 **2.1×**；按版面归一化后是 **1.57×**（因为我们的版面更高）。
- **本作的 P95 反而比 TH20 低**（0.320 vs 0.402）：说明 TH20 的**极速弹更极端**，我们更"均匀"。
- 但**中位反应窗口本作短 36%**（4.76s vs 7.47s）⇒ 常态弹幕对我们的压迫更强。

### 3.2 判定容差（**可比；结论与初稿相反**）

**新增确证**：TH20 的 `base_radius` = **3.0f**——`stage_reset.cpp:21` 写入
`player.normal_radius = player.focus_radius = 3.0f`，由 `collision.cpp:14` 按聚焦状态读
（`owner.hpp:37` 字段，`offsetof == 0x2094`）。**注意**：聚焦与非聚焦**都是 3.0f**，TH20 不靠"聚焦缩小判定"。

| 来源 | 弹半径中位 | 自机半径 | 容差 `gap` | **gap / 版面高** |
|---|---|---|---|---|
| **TH20（实际：判定因 bug 为 0）** | 2.40 | **0** | 2.40 | **0.0054** |
| 本作（自机 r=0，有意点判定） | 3.00 | 0 | 3.00 | **0.0050** |

⇒ **两边都是点判定，容差只由弹半径决定，归一化后差 8%。**
即：**判定这一项两边实质相同**——TH20 的 0 是"本该有 3.0 却没写进去"的 bug 结果，
我们的 0 是 `js/config.js:80` 的显式设定（`js/entities.js:222` 直接取用）。

**两边判定路径的公式形式也一致**：
- TH20：`dist² >= 0² + r_bullet²`（`collision.cpp:48`，`percent × 3.0 / 100 = 0`）
- 本作：`dist² >= (0 + r_bullet)²`（`js/collision.js`，`pr + b.r` 且 `pr = 0`）

**为什么 TH20 会变成 0（机制解释，可信但未直接验证）**：
`collision_percent`（`player+0xe8`）在恢复出的代码里**没有任何 gameplay 层写入者**；
`construct_player`（`game_session/session.cpp:6-12`）也不写它。若该字段保持 0，
则 `0 × base_radius(3.0) / 100 = 0`，命中判定退化为点判定——与用户所述"因为 bug 而为 0"一致。
（`base_radius = 3.0f` 本身是确证的：`stage_reset.cpp:21`。）

**结构性差异（这才是关键）**：
- 本作 `r_player = 0` ⇒ 难度**完全由弹半径决定**，没有"缩小自机判定"这层设计空间；
- TH20 有 `collision_percent`（0..100 可调）与 `expanded_collision`（×3.6）两条外部调参通道。

## 4. 反应时间窗口（难度的第一性量）

对某一发弹，从"进入自机可反应纵向距离"到"命中"的时间估计：

```
T_reaction = d_approach / (speed × 60)
```

`d_approach` 两边都取 `H × 0.75`（本作 450px / TH20 336px）——**这是估计量**，真实值取决于该面敌机停留位置。

| 来源 | 反应窗中位 | 以 P95 速度计 | 近身假设（`H×0.55`） |
|---|---|---|---|
| TH20 | **5.60s** | 1.87s | 4.10s |
| 本作（面 1） | **3.57s** | 2.68s | 2.62s |
| 本作（EX） | **4.69s** | 1.30s | 3.44s |

⇒ **本作常态窗更短（更难），TH20 极端弹更快（P95 窗更短）**。两种"难"的性质不同：
TH20 是"偶尔极快"，本作是"整体偏快且量大"。

## 5. 【必须读】口径差异与不可比项

**这些限制会改变结论的解读方向，不能省略。**

1. **本作是自由运行沙盒**：自机固定不动、敌机不死、章节不结束，因此
   - 弹/秒代表**峰值负载**，不是实际游玩中玩家面对的密度（玩家击破敌机会降低它）；
   - 章节总弹数**随观测时长线性增长**（实测 900 帧 → 97,894 发；3600 帧 → 460,035；7200 帧 → 943,153），
     ⇒ **"每面总弹数"不是内容属性**，只有**率**有意义。这是本模型最重要的一处修正。
2. **TH20 是脚本静态值**：`ins_601` 的触发发生在循环/条件里，静态计数**无法得到"每秒发弹数"**。
   `wait_after`（开火后最近的 `ins_23`）**不等于**该队列的重复间隔——它是脚本下一个状态转换的等待。
   ⇒ 本报告**不给 TH20 的 发/秒**，只在 §3.3 给出可确证的分项（开火次数、单次弹数、等待中位）。
3. **TH20 的 46% 开火没有字面量速度**（`ins_605` 传的是变量如 `[-1.0f]` / `%E`）
   ⇒ §3.1 的 TH20 速度分布只覆盖 150/278 条开火，**存在选择偏差**（有字面量的往往是最简单的弹）。
4. **rank 难度变体**：TH20 同一发射在不同难度有不同参数（`!E67/!N67/!H67/!L67` 包裹）。
   本提取按"最近一次覆盖"取到**其中一档**，未区分难度 ⇒ TH20 数值是**混合难度**。
5. **本作自机判定 = 0**：`gap` 完全由弹半径决定，与 TH20 的"可调判定"机制不同构，
   所以 §3.2 的对比是**下界对比**（TH20 实际容差 ≥ 表中值）。
6. **两边自机机动能力不可比**（TH20 速度数值不可得）⇒
   **无法计算"单位时间可移动多少个容差"**，那是"可躲避性"的真正度量。**这是本模型最大的缺口。**

## 8. 子代理补充数据的核对与新增结论

独立提取（`~/tmp/th20/th20_extract.py`，只读、不写文件）与我的 `v3.py` 交叉核对：

| 项 | 我的 v3.py | 子代理 | 一致？ |
|---|---|---|---|
| `ins_601` 总数 | 278 | 278 | ✅ |
| 出怪指令总数 | 514 | 514 | ✅ |
| 50 弹种半径 | 解出 | 解出 | ✅ |
| 字面量速度覆盖 | 150/278 | 150/278 | ✅ |
| `base_radius` | 不可得 | **3.0f**（`stage_reset.cpp:21`） | ✅ 我复核确认 |
| `collision_percent` 适用范围 | — | 称"仅 `flags & 16`" | ❌ **我为误**：`collision.cpp:48,57` 无条件应用 |
| 自机速度数值 | 不可得 | 仍不可得（无 `.sht`） | ✅ 一致缺项 |

### 8.1 【新增·重要】TH20 的 ECL **没有无限循环** ⇒ 时间轴是有限的

子代理穷举：全 21 个文件 `grep 'if (1) goto' | grep -v @` = **0 命中**。
每一条 `if (1) goto L @ n` 都带 `@ n`，是**异步子程序派生**（266 条），不是回边。
重复只来自计数循环 `if ($X--) goto L @ 0`，迭代数取字面量初值。

**含义**：
- 每面 `Σ ins_23` 是**有限且可算**的 ⇒ 可以给出"该面脚本时间轴总长"这一**可比量**；
- 例如 `st01.ecl` 的 `Σ ins_23 ≈ 25,793–27,507` 帧 ≈ **7.2–7.6 分钟**（Lunatic）；
  这与"一面道中约 7–8 分钟"的实际游玩时长同量级，**是一个可信的交叉验证**。
- 对比之下，本作的章节时间轴是**玩家行为驱动**的（道中靠 `duration`、Boss 靠击破），
  所以"面时长"不可直接与 TH20 的脚本时长对齐——**只能比"率"，不能比"总时长"**（见 §5.1）。

### 8.2 仍然不可比的两项（最终状态）

1. **TH20 自机速度**：仍不可得（`plNN.sht +0x10`，无 `.sht` 文件）。
   ⇒ 无法计算"单位时间可移动多少个 `gap`"，而**那才是可躲避性的真正度量**。本模型的最大缺口。
2. **TH20 的发/秒**：静态脚本 + 计数循环，无法从文本直接得出。
   子代理给的"估算总弹数 13,508"（235 次开火 × `count×rows` 之和）是**跨全部子程序与全部难度的求和**，
   既不对应单次游玩、也不对应单个难度，**本模型不采用它作为体量指标**。

### 8.3 修正后的总判断

把各项合并。**判定这一项已归零为「实质相同」，所以差异只剩下「速与量」**：

| 维度 | TH20 | 本作 | 谁更难 |
|---|---|---|---|
| 弹速（屏高/秒，中位） | 0.134 | **0.210** | 本作 |
| 反应窗（中位速） | **5.60s** | 3.57–4.69s | 本作 |
| 容差（gap/H，点判定） | **0.0054** | 0.0050 | 实质相同（差 8%） |
| 弹幕吞吐（发/秒） | 不可比（口径不同） | 180–2084（峰值） | 未知，但量级差明显 |
| 极速弹（P95 屏高/秒） | **0.402** | 0.320 | TH20（偶发更极端） |
| 自机机动 | **不可得** | 6.8 / 2.15 px/帧 | 未知 |

⇒ **本作在"常态弹速、反应窗"两项上更紧；容差两边实质相同**；TH20 只在**极速弹的尾部**更极端。
但**因为自机速度不可得，仍不能断言「本作整体更难」**——如果 TH20 的自机明显更慢，它更长的反应窗反而可能是优势；**容差这一项已不再是变量**（两边都是点判定）。
